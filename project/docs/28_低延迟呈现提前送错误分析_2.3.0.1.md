# 2.3.0.1 低延迟呈现提前送错误分析

日期：2026-11-26。对象：`ngb-recomp-native` 分支 `release-2.3`，已发布版本 **2.3.0.1**。  
结论先行：**这是低延迟呈现（`low_latency_present`）的边界逻辑错误，默认关闭；不影响普通玩家、游戏速度或存档。** 本地已有修正，但尚未发布。

## 1. 影响范围

只有满足以下全部条件才会走到：

```text
black.ini low_latency_present = 1
或命令行 --present-early 1
```

而 `d3d/device.cpp` 的调用是短路：

```text
early = g_cfg.present_early && ... && frame_clock::present_before_tick(...)
```

所以开关关闭时，`present_before_tick()` 根本不执行，游戏仍走原来的“等节拍再送”。

**因此：默认玩家不受影响。**

## 2. 现象

低延迟开启时，某些显示模式下画面可能：

- 一帧重复、一帧丢失；
- 窗口 / 无边框下不如关闭时顺；
- 真全屏 + vsync 关时，撕裂线不在画面边缘，而回到中间；
- 不会崩溃、不会改变游戏速度、不会影响存档。

## 2.1 作者对 2.3.0 提出的三个问题

作者说明，2.3.0 当时有三个问题，2.3.0.1 / 2.3.0.1-t 是为此做的修正；两者代码相同。

1. **真全屏 + vsync 关 + 固定 144/165Hz 也 hold Present**
   - 原因：VRR hold 只看“刷新率不能跟随”，没看 vsync；
   - 证据：165Hz 桌面、vsync 关的测试日志出现 `Presents held 6.25 ms`；
   - 后果：白白多约 6ms 延迟，撕裂不会更均匀；
   - 修正：`decide_hold()` 加 `tearing = exclusive && !g_cfg.vsync`，撕裂模式不 hold。

2. **低延迟呈现和“撕裂线放边缘”互相抵消**
   - 真全屏 + vsync 关 + 低延迟开启时，提前送的帧立即翻页，撕裂回到中间；
   - 低延迟默认关闭，但说明没写这个组合；
   - 作者选择：**vsync 关时低延迟不再提前**。

3. **每 2 秒在时钟线程上做完整显示查询**
   - 正常 0.2–0.5ms，但扩展坞 / 多显示器 / DisplayLink 可能很慢；
   - 时钟线程优先级最高，超过约 14ms 会让下一 tick 迟到，变成“每 2 秒顿一下”；
   - 修正：2 秒只做 `EnumDisplaySettings` 轻量比较，模式变了才完整查询；另每 30 秒完整兜底。

这三项是 2.3.0.1 的修正背景。本文的 bug 是第 2 项的实现没有完全生效：队列/vsync 检查放在 `deadline == 0` 的返回之后。

## 3. 2.3.0.1 的代码路径

`loader/src/d3d/frame_clock.cpp`：

```text
present_before_tick(now):
    deadline = g_early_deadline
    if deadline == 0:
        return true          // 直接允许提前
    if not (exclusive device with vsync):
        return false
    ...
```

问题在顺序：**先看 deadline，后看“是不是真正的 flip queue + vsync”**。

`g_early_deadline` 只在“有跟随屏幕、且一拍正好一次刷新”时非零。  
其他情况都是 0，包括：

- 窗口 / 无边框，屏幕无法被跟随；
- 120 / 240Hz，屏幕有跟随，但一拍是 2 / 4 次刷新；
- 真全屏 + vsync 关，屏幕无法被跟随。

这些情况会直接 `return true`，绕过后面的 queue/vsync 检查。

## 4. 各组合的实际结果

| 模式 | 显示 | vsync | deadline | 2.3.0.1 行为 | 是否符合发布说明 |
|---|---|---|---|---|---|
| 窗口 / 无边框 | 60Hz，可跟随，一拍一次 | 开 | 非 0 | queue 检查失败 → 不提前 | 符合 |
| 窗口 / 无边框 | 165Hz / VRR，不可跟随 | 开 | 0 | 直接提前 | 与“只在真全屏”矛盾 |
| 窗口 / 无边框 | 120 / 240Hz，可跟随，多刷新 | 开 | 0 | 直接提前 | 未定义，疑似错误 |
| 真全屏 | 60Hz，可跟随，一拍一次 | 开 | 非 0 | 用 deadline 判断 | 符合 |
| 真全屏 | 165Hz / VRR，不可跟随 | 开 | 0 | 直接提前 | 符合作者“不可跟随就照旧”的注释 |
| 真全屏 | 60Hz，可跟随，一拍一次 | 关 | 非 0 | queue 检查失败 → 不提前 | 符合 |
| 真全屏 | 165Hz / VRR，不可跟随 | 关 | 0 | 直接提前 | **与“without vsync 应等节拍”矛盾** |

## 5. 时间线：后加的判断，旧的注释

用 git 时间线可以判断哪一句是旧规则、哪一句是后来收紧的意图。

| 时间 | commit | 内容 |
|---|---|---|
| 15:13 | `db5f92f` | `present_before_tick()` 先看 deadline，`deadline == 0 → return true`；注释写“不可跟随就照旧提前” |
| 17:51 | `49c45f9` | 把 `g_early_composed` 改成 `g_early_queued`，commit message 明写“present_early now applies only to exclusive fullscreen with vsync”；validation 写“window/borderless and vsync off stay at their tick” |

关键在 `49c45f9` 的 diff：

- 它新增了 `if (!g_early_queued) return false;`；
- 但这段仍然放在 `if (!deadline) return true;` **后面**；
- 所以 deadline 为 0 时，新增的 queue/vsync 检查根本不会执行。

同时 `49c45f9` 更新了 `frame_clock.h` 的前半段（加上“with vsync”“without vsync frames wait”），但没有删掉最后那句“where the display is not followed the frame goes at once”。

结论：

```text
“deadline == 0 → return true” 是 15:13 的旧规则
“only exclusive + vsync” 是 17:51 后来加入的明确意图
queue 检查放错位置，是 49c45f9 的实现遗漏，不是作者有意保留
最后那句“不可跟随就照旧”是旧注释，没有跟上 49c45f9 的收紧
```

所以对 **窗口 / 无边框 / vsync 关** 来说，这不是“规格冲突”，而是明确的代码错误：`49c45f9` 的 commit message 已经说它们应该等节拍。

作者后来给的 2.3.0.1 意图也确认：

```text
1. 真全屏关 vsync 不再推迟 Present
2. 真全屏关 vsync 时低延迟不再提前
6. 低延迟需要真全屏并打开 vsync
```

所以“queue 成立、但 deadline 为 0”的情况（120/240 多刷新、165/VRR 不可跟随）不应再额外收紧；保持原来的 at-once 路径即可。

## 6. 本地修正

本地 commit 修正如下：

```text
1. 先问 host3d::present_flip()：
   目前 device 是不是真正的 exclusive flip queue？
2. 再要求 g_cfg.vsync：
   vsync 关不提前。
3. 通过前两步后，如果没有 deadline：
   保持旧的“画完就送”，不额外等待。
```

这样做的取舍：

- 窗口 / 无边框：不提前；
- vsync 关：不提前；
- 60Hz 真全屏 + vsync：用 deadline；
- 120 / 240Hz、165Hz / VRR 的真全屏 + vsync：保持旧 at-once 路径，不引入新行为。

## 7. 为什么说只影响低延迟开关

- `present_before_tick()` 只在 `g_cfg.present_early` 为 true 时调用；
- `g_early_*` 只在这个函数和每分钟日志里使用；
- `before_present()` 的 hold 逻辑本来就用 `g_cfg.present_early` 分支；
- `host3d::present_flip()` 只是新增只读 accessor；
- 开关关闭时，这些代码不参与决策。

所以：

```text
low_latency_present = 0：
  本次修正没有行为变化

low_latency_present = 1：
  只改变“哪些情况允许提前送”
```

## 10. 还要向作者确认的问题

作者已经确认：

```text
低延迟需要真全屏 + vsync
真全屏关 vsync 不提前
```

还需要确认的是“真全屏 + vsync 开、但没有 deadline”的两种情况：

1. **120 / 240Hz（有跟随，但一拍 2 / 4 次刷新）**  
   低延迟应该保持 at-once，还是等节拍？  
   目前 2.3.0.2 保持 at-once，没有新增等待。

2. **165Hz / VRR（完全不可跟随）**  
   是否保留 at-once？  
   目前 2.3.0.2 保留。

3. **窗口 / 无边框**  
   作者第 6 点写“低延迟需要真全屏 + vsync”，所以 2.3.0.2 让窗口完全不提前；  
   如果作者认为窗口在不可跟随显示上仍应保留 at-once，需要再调整。

4. **2.3.0.1-t 与 2.3.0.1 是否完全同一份代码**  
   作者说是；如果之后确认不是，需要重新对照测试包。
